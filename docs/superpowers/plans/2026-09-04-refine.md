# GymOps frontend refinement (Phase 7d)

## Context

Phase 7c (PR #11, 2026-09-04) gave GymOps its visual system: DESIGN.md, tokens, pill buttons, 44 px controls, the shared layer (`PageHeader`, `EmptyState`, `LoadingState`, `StatusBadge`). Three surveys of the current `main` (eb36f23) show the system is sound but adoption is partial, and several standard affordances are hand-rolled where a shadcn primitive exists. Concretely:

- 10 raw `<input type="checkbox" className="size-4">` (16 px) including the checklist tick, the app's core interaction, which violates the 44 px rule.
- 4 copy-pasted delete-confirm `Dialog`s and 5 destructive actions with no confirmation at all.
- `toast()` is never called; successes after navigation or dialog close are silent, and errors in unmounted dialogs are lost.
- The vendored `Tooltip` is unused; 4 `title=` attributes stand in for it, one on a disabled button where it never shows.
- Admin has no `h1` and a hand-rolled underline tab bar; 5 segmented filters are `aria-pressed` button rows.
- A polish backlog: 15 `rounded-md` surfaces, the bell badge in red instead of violet, 7 copies of the native-select class string, 16 hand-styled section headings, 11 bare-paragraph empty/loading states, `min-h-9` on the chat composer.

Register: **product**. Users are 20–25-year-old staff on a phone mid-shift (PRODUCT.md). Everything below stays inside DESIGN.md and the closed decisions in PROJECT_SPEC.md §4 (light only, native selects stay native, bottom tab bar, no route transitions).

**Scope agreed with Rami:** core primitive set (checkbox, alert-dialog, tabs, toggle-group, tooltip and toast wiring) plus the polish sweep. One branch, one PR, one commit per task. **Deferred**, logged under Later: sheet + five-tab phone bar, command/cmdk, progress, collapsible, scroll-area, react-hook-form, calendar.

### P7D-04 Toast wiring

Rule (goes into DESIGN.md and §4): inline `role="alert"` stays for errors on a form that is still on screen. A toast is used only when the result leaves the screen (navigate, dialog close) or the action has no form at all (a toggle). No toast for the user's own checklist ticks or chat sends; principle 3, "quiet unless it matters". Success toasts are short nouns ("Post published", "Invitation sent"); error toasts carry the existing `*.error` string.

`toast` is called from the feature code, not the shared hooks, because the message depends on the screen. Sites:

- Navigate-away successes: `post-editor.tsx:100,103`, `guide-editor.tsx:108,111`, `template-editor.tsx:143`, `post-detail.tsx:126` and `guide-detail.tsx:124` (delete; also surface the error, which today dies with the dialog), `chat-page.tsx:217,272`

- Fire-and-forget toggles, error toast at minimum: `checklists/templates-page.tsx:89`, `admin/gyms-panel.tsx:88`, `admin/users-panel.tsx:152` (success too: deactivating a person is consequential), `news/news-feed.tsx:77`, `news/post-detail.tsx:76`, `chat/chat-page.tsx:233`, `incidents/incident-detail.tsx:54,69`, `notifications/inbox-page.tsx:34,77,116`
- Destructive without feedback: `message-list.tsx:172`, `entry-card.tsx:158`, `channel-members-dialog.tsx:82` (error toast; success is visible in the list)
- Checklist sync `checklists/use-run-sync.ts`: one error toast when a tick fails to sync ("Not saved, will retry"), nothing on success

`sonner.tsx` is already tuned (bottom-center, safe-area offset above the tab bar). Add `richColors={false}` and map success/error icons to the tone tokens (`bg-tone-success-bg` etc.) via `toastOptions.classNames`.
