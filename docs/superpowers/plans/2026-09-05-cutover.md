# Hosted Cutover Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Several tasks are operations in the Supabase, Cloudflare and GitHub dashboards rather than code; those steps say exactly what to click or run and what to record afterwards.

**Goal:** Take GymOps off the local stack for the first time: the hosted Supabase project, the web app on Cloudflare Pages, real mail, real push, a first desktop release, and one gym piloting it — plus the two fixes that should land before 200 people see the app.

**Architecture:** Nothing new is built. The database, functions and auth settings already exist as migrations and `config.toml`; this phase applies them to the hosted project `ngcqpftfqepvhpjikaqq`, puts the built web bundle on Cloudflare Pages behind an SPA rewrite, wires every secret the spec keeps out of the repo, and walks the open lines of `docs/walkthrough.md` against the deployed origin. The pilot runs on the origin Pages assigns (`https://<project>.pages.dev`); the custom domain comes later and is one Site URL change plus a redirect-list edit.

**Tech Stack:** Supabase CLI 2.116 (`link`, `db push`, `functions deploy`, `secrets set`), Cloudflare Pages (Git integration, `npm run build`, `dist/`, `public/_redirects`), Resend (SMTP for auth mail, API for notifications), GitHub Actions `release.yml` (tauri-action to `gymops-releases`), Playwright + Mailpit locally for the two code tasks.

Decisions taken with Rami on 2026-09-05: **Cloudflare Pages**; **the host's default domain for the pilot**, not a boulders.dk subdomain yet; scope is **the cutover plus two pre-cutover fixes** (admins reaching gym channels, branded auth mail). Out of scope: the phone More sheet, code signing certificates (installers stay unsigned for the pilot), Sentry source maps, the issue → incident link.

## Global Constraints

- Schema changes only via `supabase/migrations`; every table has RLS with pgTAP tests (spec §5). **Never `db reset` against hosted; never let `supabase/seed.sql` or `supabase/seeds/` near it** (they hold pgTAP helpers and four users with a published password).
- All client variables are `VITE_*` and ship in the bundle; secrets live only in Supabase function secrets and GitHub Actions secrets (spec §5, README).
- No hard-coded UI strings; every new key in both `src/locales/en/common.json` and `src/locales/da/common.json` (parity test `src/lib/i18n.test.ts`). Danish runs long.
- Components never import `@/lib/supabase`; data access in a feature's `queries.ts`. No reaching into another feature's files (`no-restricted-imports`).
- Gates after every code task: `npm run typecheck && npm run lint && npm run format:check && npm test`; `npm run db:reset && npm run db:test` when SQL changes.
- Work on a branch in a worktree (`.claude/worktrees/cutover`, dev server on **5174**; copy `.env.local` and `supabase/functions/.env` from the primary checkout — both gitignored). Never switch branches in the primary checkout.
- Finishing a task = same commit updates `PROJECT_STATE.md` (task row, the cutover checklist ticks, blockers, decisions log) and `PROJECT_SPEC.md` §3.2/§4 where layout or a decision changed. Commits reference the task id, e.g. `feat(chat): admins browse gym channels (P9-01)`.
- Every dashboard value that the code depends on (origin, keys, VAPID public key) is recorded in `PROJECT_STATE.md` under "Hosted project cutover" the moment it exists, so the next session does not have to find it again.

### Task P9-01: Admins reach every gym channel through Browse

The gap (PROJECT_STATE "Known gaps", found by P7-07): `channels_select` lets an admin read every gym channel and `can_moderate_channel()` lets them delete there, but the sidebar lists only channels one is seated in (`channel_members!inner`) and Browse offers custom channels only, so an admin can neither read nor moderate a gym they hold no membership in. Fix chosen: **Browse lists gym channels the caller may read but is not in; Join seats them.** `channel_members_insert` already allows a self-join into any non-DM, non-private channel where `can_read_content(gym_id)` holds, which for an admin is every gym. - [ ] **Step 3: Widen the query and the type**

In `src/features/chat/queries.ts`:

```ts
export type JoinableChannel = Pick<
  Channel,
  'id' | 'kind' | 'gym_id' | 'name' | 'description' | 'is_private'
> & { members: number }

/**
 * The channels this person may see and has not joined: `channels_select`
 * decides the list — a public custom one in a gym they read, a private one
 * they moderate, and (P9-01) the gym channels an admin may read without a
 * membership, so head office can open any gym's chat. DMs are never browsed
 * and `#company` seats everyone by trigger, so neither is asked for.
 */
export function useJoinableChannels() {
  const { user } = useAuth()
  const userId = user?.id

  return useQuery({
    queryKey: [...chatKeys.joinable, userId],
    enabled: Boolean(userId),
    queryFn: async (): Promise<JoinableChannel[]> => {
      const { data, error } = await supabase
        .from('channels')
        .select(
          'id, kind, gym_id, name, description, is_private, channel_members(user_id)',
        )
        .in('kind', ['custom', 'gym'])
        .order('name')

      if (error) throw error

      return data
        .filter((channel) => !channel.channel_members.some((m) => m.user_id === userId))
        .map(({ channel_members: members, ...channel }) => ({
          ...channel,
          members: members.length,
        }))
    },
  })
}
```

## Risks and what to watch

1. **The origin moves later.** Everything in P9-05 (Site URL, redirect list), P9-06 (`SITE_URL`), Pages and the installed PWAs points at `gymops.pages.dev`. When the boulders.dk subdomain arrives: Pages → Custom domains, then Site URL, the redirect list, `SITE_URL` in secrets, and every phone reinstalls the PWA (push subscriptions are per origin). Budget an hour; it is a checklist, not a project.
2. **Unverified Resend domain** silently turns every invite into a 403 at SMTP. Do P9-05 Step 1 first and wait for Verified before inviting anyone.
3. **VAPID pair mismatch** between Pages and the function secret refuses every subscription with a 401/403 in `notify`'s logs. Generate once, paste twice from the same output.
4. **`db push` stops halfway** on a hosted-only difference (extension privileges are the likely one). Fix forward with a new migration; never edit an applied file, never reset.
5. **Unsigned installers** need the right-click → Open dance on every Mac; say so in the message that hands them out, or keep the pilot on the PWA and the browser and release the desktop app to head office only.
6. **The assistant answers "could not answer"** until the Anthropic organisation has credits; the pilot does not depend on it.
7. **Preview deployments** get `https://<hash>.gymops.pages.dev` origins; the glob in the redirect list lets sign-in complete there, but push subscriptions made on a preview are junk — do not test push on a preview.
